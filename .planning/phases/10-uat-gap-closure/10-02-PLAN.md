<objective>
Fix fuzzy matching algorithm to be segment-aware and handle the wt-prefix pattern.

Purpose: The current `findClosestMatch()` uses pure Levenshtein distance with `maxDistance=3`.
When worktree basenames follow the pattern `{repo}-{name}` (e.g., `wt-feat-1`, `wt-feat-2`),
searching for "feat" has Levenshtein distance 5 from "wt-feat-1" (exceeds threshold) but
distance 3 from "wt" (within threshold). This causes wrong suggestions: `wt goto feat`
suggests "wt" instead of "wt-feat-1".

The fix: implement a scoring system that combines Levenshtein distance with substring/segment
awareness. Candidates containing the input as a substring or dash-separated segment get
strong preference.

Output: Segment-aware fuzzy matching that correctly suggests worktrees by segment content.
</objective>

    ```
    func findClosestMatch(input string, worktrees []Worktree) string {
        input = strings.ToLower(input)
        var bestMatch string
        bestScore := 0  // higher is better

        for _, wt := range worktrees {
            basename := strings.ToLower(filepath.Base(wt.Path))
            score := matchScore(input, basename)
            if score > bestScore {
                bestScore = score
                bestMatch = filepath.Base(wt.Path)  // preserve original case
            }
        }

        return bestMatch
    }
    ```

    New `matchScore` function that returns a score (0 = no match, higher = better):

    ```
    func matchScore(input, candidate string) int {
        // Priority 1: Exact segment match (split on "-")
        // "feat" matches segment in "wt-feat-1" -> score 100
        segments := strings.Split(candidate, "-")
        for _, seg := range segments {
            if seg == input {
                return 100
            }
        }

        // Priority 2: Substring match
        // "feat" is substring of "wt-feature" -> score 80
        if strings.Contains(candidate, input) {
            return 80
        }

        // Priority 3: Segment prefix match
        // "fea" matches start of segment "feat" in "wt-feat-1" -> score 60
        for _, seg := range segments {
            if strings.HasPrefix(seg, input) {
                return 60
            }
        }

        // Priority 4: Input is a prefix of candidate
        // "wt-f" matches start of "wt-feat-1" -> score 40
        if strings.HasPrefix(candidate, input) {
            return 40
        }

        // Priority 5: Levenshtein distance (for typos)
        // "featur" vs "feature" -> distance 1 -> score 20
        dist := levenshteinDistance(input, candidate)
        maxDist := max(3, len(input)/2)  // scale threshold with input length
        if dist <= maxDist {
            return 20 - dist  // closer = higher score (max 20, min 17 for dist=3)
        }

        // Also check Levenshtein against individual segments
        // "fea" vs "feat" -> distance 1 -> score 15
        for _, seg := range segments {
            dist := levenshteinDistance(input, seg)
            if dist <= 2 {
                return 15 - dist
            }
        }

        return 0  // no match
    }
    ```

    Add the `max` helper if not available (Go 1.21+ has built-in max for int, but check go.mod version):
    - Check `go.mod` for Go version. If >= 1.21, use built-in `max`.
    - If < 1.21, add a simple helper:
      ```
      func maxInt(a, b int) int {
          if a > b { return a }
          return b
      }
      ```

    The `strings` import is already present in resolve.go. No new imports needed.

    WHY this approach:
    - Exact segment match (score 100): "feat" is literally a segment of "wt-feat-1"
    - Substring match (score 80): "feat" is inside "wt-feature"
    - Segment prefix (score 60): "fea" starts segment "feat"
    - Levenshtein (score 20): "featur" is a typo of "feature" (fallback)
    - The old approach gave "wt" (distance 2) higher rank than "wt-feat-1" (distance 7)
    - The new approach gives "wt-feat-1" score 100 (exact segment) vs "wt" score 0
